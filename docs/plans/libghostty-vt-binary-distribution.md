# Ship libghostty-vt as a prebuilt binary

Goal: an app that depends on Tessera by version links libghostty-vt on macOS, Linux, and Windows without Zig, CMake, or a local build, and Tessera's own test, docs, and VM jobs stop building Zig. Tessera's CI builds the pinned revision once into an SE-0482 static-library artifact bundle, publishes it as a prerelease asset, and `Package.swift` references it by URL and checksum. You see it when a CI job consumes Tessera by version from a clean machine and runs a Ghostty round trip, and when no test job's log mentions Zig.

## Approach

Current state. `CGhosttyVT` (`Sources/CGhosttyVT/`: `CGhosttyVT.h`, `module.modulemap`, `shim.c`) links a libghostty-vt that each machine builds with Zig 0.17.0 from the pin in `scripts/ghostty-vt-version.txt` (`f54340ad`) through `scripts/build-libghostty-vt.sh` and `.ps1`, into `~/.cache/tessera/libghostty-vt/<rev>/<platform>-<arch>/` (Windows `%LOCALAPPDATA%\tessera\libghostty-vt`). `Package.swift:520-593` computes that path and passes it in `.unsafeFlags` with an absolute rpath; the build scripts copy Ghostty's headers into `Sources/CGhosttyVT/include/ghostty/`, which `.gitignore` excludes. Every consumer of the build runs the Zig step first: the `core:build`, `core:test`, `core:test-coverage`, `docs:targets`, and `ci:build-test` mise tasks, the `test` and `test-parallel` jobs in `.github/workflows/ci.yml`, `docs.yml`, `pages.yml`, the Lima tasks (`scripts/vm.py:653`), and the Windows guest (`scripts/run-windows-tests.ps1`).

End state. The headers are committed. `CGhosttyVT` stays a source C target and depends on a `binaryTarget(name: "GhosttyVTLibrary", url:, checksum:)` whose artifact bundle carries only `libghostty-vt.a` (or `ghostty-vt-static.lib`) per triple, plus `.linkedLibrary("ntdll", .when(platforms: [.windows]))`. No `.unsafeFlags` remain. A workflow, `.github/workflows/ghostty-vt.yml`, builds every variant on hosted runners when a `ghostty-vt-<short-sha>` tag is pushed and publishes the zip and its checksum to a prerelease of that tag. Contributors who bump the pin build a bundle locally with one script and select it with an environment variable until the new release exists. A CI job consumes Tessera by version through a `file://` git tag and runs a Ghostty round trip on all three platforms.

Patterns to follow. The spike in `spikes/GhosttyDistribution/` (tag `0.3.x` patches) and its research record, [libghostty-vt distribution](../research/libghostty-vt-distribution.md), are the reference layout; Findings §5 there lists the build flags each platform needs (`-Dsimd=false` on Windows, `-Dcpu=baseline` on Linux). Reuse the existing build scripts as the one way to compile libghostty-vt; the new packaging script only arranges their output. Workflow steps pin actions by SHA, as the existing workflows do. The bundle's `info.json` follows SE-0482's `staticLibrary` artifact type, with Ghostty's `LICENSE` beside the libraries.

Patterns to avoid. Headers or a module map inside the bundle (fails on Xcode 26.6 and Swift Build 6.3.3, research §4). Committing binaries to the repository. A second way to compile libghostty-vt. Keeping `.unsafeFlags` as a fallback path.

Files that orient a newcomer. `Package.swift` (the `CGhosttyVT` and `GhosttyVT*` blocks), `scripts/build-libghostty-vt.sh`, `scripts/build-libghostty-vt.ps1`, `scripts/ghostty-vt-version.txt`, `.github/workflows/ci.yml` (the `test` job's Ghostty steps), [Updating Ghostty VT](../guides/updating-ghostty-vt.md), and the research record.

Non-goals. Making the Ghostty-backed harness optional (the research's runner-up). Upstreaming anything to Ghostty. Changing the Ghostty pin. Releasing a Tessera version.

## Decisions

- 2026-10-22 Ship libghostty-vt as an SE-0482 static-library artifact bundle with the headers committed in a source `CGhosttyVT`, built by Tessera's CI once per pin and published as a release asset, because no upstream artifact covers Linux and Windows and the spike proved this layout by version on all three platforms. (owner, from [libghostty-vt distribution](../research/libghostty-vt-distribution.md); plan 036 Decision 9 (ii))
- 2026-10-22 The bundle is published from this repository as `ghostty-vt-<short-sha>` prereleases marked not latest, beside Tessera's own `v<SemVer>` releases, rather than from a separate repository, because tags and releases are independent on GitHub and one repository keeps the producer workflow, the pin, and the manifest's URL in one change. The owner authorized the first tag and prerelease for an unattended run. (owner)
- 2026-10-22 The build scripts re-vendor the committed headers with `--update-headers` (`-UpdateHeaders` on Windows), and `build-libghostty-vt.sh` takes `--target <zig-target>` for the cross-built variants (macOS x86_64, a glibc floor, musl), because the plan keeps the build scripts the one way to compile libghostty-vt and its Slice 6 flow needs a re-vendor step. Variant directories are named by the build scripts' install labels (`macos-universal`, `linux-arm64`, `linux-musl-x86_64`, `windows-arm64`, …), and the packaging scripts regenerate `info.json` from the directories a bundle holds, so merging needs no JSON parser. (agent)
- 2026-10-22 `ghostty-vt.yml` also runs on pull requests that touch the producer (build, package, and audit, never publish), because `workflow_dispatch` only works once the workflow is on `main` and the one authorized tag cannot be moved, so the workflow had to be proven before the tag was pushed. (agent)
- 2026-10-23 Remove the `pull_request` trigger from `ghostty-vt.yml` (`76fd847`), superseding the decision above once it had served: it reran seven builds on every push to a pull request that touched the producer. A dispatch on a branch builds without publishing, and a tag run publishes only a complete bundle. (owner)
- 2026-10-23 After an independent review (agent `GhosttyBundleCritic`), the producer refuses to replace a published zip and refuses an incomplete bundle unless a `workflow_dispatch` run opts in with `replace-assets` or `allow-partial`, and its artifact uploads overwrite so `gh run rerun --failed` reaches the publish step (`9bfc507`), because `Package.swift` pins the zip's checksum and a rebuilt zip never has the same bytes. The packaging scripts refuse a variant whose triples another variant already claims. (agent, after review)
- 2026-10-23 Ship the licenses of every third-party component linked into the archives in the bundle as `THIRD_PARTY_LICENSES/`, from `scripts/ghostty-vt-licenses/`, and list them in `THIRD_PARTY_NOTICES.md` (`9bfc507`), because Ghostty's MIT license covers only Ghostty's code and each component's license requires its notice in binary redistributions. Dual-licensed components are redistributed under their BSD or MIT option, which avoids Apache-2.0's NOTICE handling. (owner asked for the technically right answer; agent)
- 2026-10-23 Cover the bundle's x86_64 macOS and musl variants in CI rather than locally: a `macos-26-intel` leg of `version consumer` and a `static Linux SDK` job (`9eac8e8`). `TesseraTerminalIO` imports `Musl` when `Glibc` is absent, so the library targets build with the Static Linux SDK, and `mise run linux:build` uses a swift.org toolchain through swiftly on macOS and stops with that advice when none is installed. (owner: no Rosetta on the host; agent)
- 2026-10-23 Resolve the resolved files (root, `Examples`, and the workspace) with the Swift 6.4 lane, pass `--only-use-versions-from-resolved-file` from every repository entry point, and check them in every CI `test` leg (`bb09a56`, `9eac8e8`, and the follow-up to the second review), because xctest-dynamic-overlay's Swift 6.4 manifest adds swift-issue-reporting, Swift 6.3.3 prunes that pin on a plain command, and the flag is the only form both lanes leave unchanged. (owner asked; agent, corrected after review F7)
- 2026-10-23 Republish the pin's bundle as `ghostty-vt-f54340ad7781-r2` so it carries `THIRD_PARTY_LICENSES/`, then delete the `ghostty-vt-f54340ad7781` release and tag, because nothing outside this pull request referenced them. ## Discoveries

- The glibc floor of both glibc variants is `GLIBC_2.27`, built with `-Dtarget=<arch>-linux-gnu.2.28` — `objdump -T` of the shared library from the same build, in run 39893033267 (`linux-x86_64` and `linux-arm64` legs) and in the Lima guest. The research's `arc4random_buf` (glibc 2.36) is gone at that target. The static archive itself carries no symbol versions, so the check reads the `.so` built beside it.
- Every variant built on the first run, cross-compiled where the runner differs: `x86_64-macos` from the arm64 `macos-26` runner (then `lipo` into `macos-universal`), both musl variants from `ubuntu-latest`. The zip is 32.3 MB; the archives are 21–27 MB each and the Windows `.lib` files 10–11 MB — run 39894494863.
- `swift package experimental-audit-binary-artifact` takes an archive (zip, tar, tar.gz), not a library, and audits only the variant matching the host triple, so the workflow audits each glibc leg's own one-variant bundle on its native runner (`Artifact is safe to use on the platforms runtime compatible with triple: x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu`). No runner has a musl host triple, so the musl variants are not audited.
- The repository's Actions policy allowed only GitHub-owned actions plus `SwiftyLab/setup-swift`, `jdx/mise-action`, and `mlugg/setup-zig` when this plan ran. The first workflow run, using `softprops/action-gh-release`, ended in `startup_failure` (run 39892930588), so the workflow publishes with the runner's `gh`. The owner has since allowed `softprops/action-gh-release@*` (`gh api repos/robfeldmann/tessera/actions/permissions/selected-actions`), so `.github/workflows/release.yml` can use it; the producer keeps `gh`, which its replace guard needs anyway.
- SwiftPM on Linux needs `unzip` to unpack the binary artifact (`error: failed validating archive … could not find executable for 'unzip'` in the Lima guest, which lacked it). GitHub's Ubuntu runners have it; `scripts/config/lima/tessera-linux.yaml` now installs it, and the guide lists it as a Linux prerequisite.

- The `version consumer` legs and `static Linux SDK` are required status checks in the `Default branch` ruleset since 2026-10-23, added by the owner beside `CI gate`, `conventional commits`, `lint`, the three baseline `test` legs, `Documentation gate`, and `DocC validation (macOS)`.

Reusing a tag name for a rebuilt zip would hit that on every cached checkout, so republishing takes a new tag and URL.

The scripts read the revision file with `Get-Content -LiteralPath | Out-String` and the headers with `[System.IO.File]::ReadAllText` on resolved absolute paths; in the UTM guest a checkout under `tess[1]` passed the header check, failed it naming `vt\color.h` and `vt\wasm.h` after a drift, and packaged a bundle.

## Outcome

Shipped. libghostty-vt for pin `f54340ad` is published as the [`ghostty-vt-f54340ad7781-r2`](https://github.com/robfeldmann/tessera/releases/tag/ghostty-vt-f54340ad7781-r2) prerelease: one SE-0482 artifact bundle with seven variants covering macOS arm64 and x86_64, Linux glibc (2.27 floor) and musl for x86_64 and aarch64, and Windows x86_64 and aarch64, with the linked components' licenses, built by `.github/workflows/ghostty-vt.yml`. `Package.swift` links it by URL and checksum through a source `CGhosttyVT` with committed headers and no `unsafeFlags`, so a fresh clone builds and tests on every lane without Zig. The `version consumer` CI job proves the by-version path on macOS (arm64 and x86_64), Linux, and Windows, and `static Linux SDK` builds and runs it with musl; both are required checks. CI, DocC, and the VM tasks no longer build Ghostty. A pin bump builds locally, re-vendors the headers, tests with `TESSERA_GHOSTTY_VT_BUNDLE=local`, and publishes with one tag ([Updating Ghostty VT](../guides/updating-ghostty-vt.md)); [libghostty-vt distribution](../architecture/libghostty-vt-distribution.md) keeps the rule.

Remember that a published `ghostty-vt-*` zip is permanent once any `Package.swift` points at it (republish under `-r<N>`), and that SwiftPM needs `unzip` on Linux.
