# Build the Phase 4 view layer with the tooling that proves it

Goal: Tessera's 1.0 view layer (styling, focus, pointer, scrolling, controls, collections, SplitView, the remaining views, and an intro app) lands component by component from the `ready` catalog docs, and every component arrives with a demo that runs live and headlessly, a scenario that an agent can run without prose, and the harness checks that catch the defect classes the archived attempts missed. ## Approach

Current state. `main` carries Phase 4 Slices 1, 2, and 2.5 (`TesseraCore`, `TesseraLayout`, the first `TesseraWidgets`: `ViewGraph` reconciliation, stacks, Flex, static `SplitView` and `ScrollView`), the omp2-reviewed design catalog in `docs/design/` (every component doc is `ready` or close to it), the amended spec (`docs/spec/phase-4/`), and the five tooling spikes under `spikes/` with the seams spike saved as `spikes/Seams/30e4bbf.patch`. Plan 034 fixed the two defects the spikes found in the runtime: nested view lists now lay out element by element (so demos can use `ForEach`), and the Examples package builds in CI. libghostty-vt comes from a prebuilt artifact bundle ([libghostty-vt distribution](../architecture/libghostty-vt-distribution.md)), so no build or test job runs Zig. The toolchain lanes are Swift 6.3.3 (baseline) and 6.4 (`docs/architecture/toolchain-lanes.md`); tasks are mise tasks (`mise run …`), and the docs are the `docs/` IWE workspace.

End state. The components of `docs/spec/phase-4/` "The 1.0 surface" are implemented and graduated into DocC, each demo is a snapshot fixture at its declared viewports, `Examples/Scenarios/` is the behaviour corpus that CI runs on macOS, Linux, and Windows, and `TesseraRuntime` (the `Application` contract, re-exported by `Tessera`), `TesseraHarness` (root package; the library app authors import to drive and check their own apps), `Examples/Sources/DemoSupport`, and `Examples/Sources/TesseraDev` (the target of the `tessera` executable) are the tooling that plan 033 designed.

Patterns to follow. Each step starts from a `ready` catalog doc (finishing it is the first part of the step). Each component lands with its tests, its demo, and its scenario in one reviewable step; port from the archive tags (`archive/phase4`, `archive/phase4-review-loop`, `archive/phase4-unicode-demo-stash`, `archive/catalog-workbench`) only after reading the code against the doc, using the port map in `docs/research/phase-4-salvage-review.md`. Measurement and `body` stay pure; every `NodeState` row has one owner; collections key by stable IDs and fail closed on duplicates. The harness never compensates for a library bug (demos find bugs; the library is fixed). Text goldens are the only committed artefacts; drift fails without `--record`. No test affordances in product API: `TesseraCore` gains only value-typed diagnostics fields, each by spec amendment. A slice that adds or changes a tool updates [Developer tooling](../architecture/developer-tooling.md) (or the per-tool page it links) and the skills before the slice is checked off, the `tessera` skill first, written as an app author sees the tool against the stable surface, then `tessera-contributing` for what only a contributor has (the `mise` tasks, the demos), so the page describes the tools as built plus what is still only designed, and agents building later slices use the skills as they go. The app contract is Decision 9 (i) and the spec's [Runtime isolation](../spec/phase-5-runtime-and-polish.md#runtime-isolation) section: `Application` carries no isolation, a host is a `@MainActor` shell over one nonisolated step that takes `isolated any Actor`, and isolation mistakes are proved by compile-fail fixtures, never by `assumeIsolated`. The harness's public names are the seven the stable-surface decision lists; every other declaration in it is `package` or internal. "Demo" is the word for Tessera's own per-component example apps; the CLI and the scenario header say `app`.

Patterns to avoid. The Showcase (a monolithic demo app) and the archived batch attempts; porting review bundles or committed captures; a `wait` that sleeps; prints as the way to answer "why".

Files that orient a newcomer. [Developer tooling](../architecture/developer-tooling.md) (what the tools are and how they fit), `docs/spec/phase-4/architecture.md`, `docs/spec/phase-4/testing-posture.md`, `docs/design.md` (status ladder, wireframes, table schemas, graduation), `docs/design/tokens.md` (viewports, roles), `docs/design/translation-key.md`, `docs/research/phase-4-salvage-review.md`, the five spike READMEs under `spikes/`, and plan 033's "Tool surface" section (kept verbatim in the cancelled plan, which this plan cites rather than repeats).

Non-goals. A `TesseraTern` backend (Tern Surface Protocol output), modal overlays, and post-1.0 views stay out.

Open questions: Decision 9 (iii) below (how an app gets `tessera`); (i) and (ii) are decided.

```swift
public protocol Application: AnyObject {
  associatedtype Body: View
  @ViewBuilder var body: Body { get }   // the root view; reads the model, hands out Bindings
  func apply(_ event: InputEvent)       // each event the graph left .ignored; resizes always

```

### 4 Registry, viewports, the main-actor driver, and `tessera launch`

Plan 032 Step 8.2 and plan 033 Step B.1, under Decision 9 (i) and the spec's [Runtime isolation](../spec/phase-5-runtime-and-polish.md#runtime-isolation) section. The contract itself landed in Slice 3, and `TerminalSession.draw` has been caller-isolated since Slice 2.

`TesseraHarness` gains two public names. `ApplicationRegistry` has `init()` and `mutating func register<App: Application>(_ name: String, minimum: TerminalSize? = nil, viewports: [Viewport], make: @escaping @MainActor () -> App)`. It is the one selection point; the harness opens factories on the main actor, once per run, so each run starts fresh and a fixture is one more registration (`register("browser-empty") { Browser(fs: .empty) }`). A duplicate name makes every entry point that reads the registry fail (exit 3, or a failing report), never last-wins; registration itself does not throw (the spike's did; do not copy it). A `@Sendable` factory for a main-actor app is a compile error at the registration site. `Viewport` is a `Hashable, Sendable` enum: `desktop` (80x24), `mobile`, `mobileScreen` (40x16), `custom(TerminalSize)`.

Everything else is `package` or internal (the step and the registry's reads are `package`; the driver and its hosts are internal, because nothing outside the harness needs them and tests reach them with `@testable import`). `TesseraRuntime` gains the canonical step, a nonisolated `package` function that takes the host's isolation as a parameter, written as the spec's [canonical step](../spec/phase-5-runtime-and-polish.md#the-canonical-step) has it (`Step.run(_ app:graph:event:isolation: isolated any Actor)`, returning the `EventDisposition`): resize the graph if the event is a `.resize`, `graph.dispatch`, `app.apply(event)` when the disposition is `.ignored` or the event is a resize (a resize is never routed, so Slice 10's routing cannot take it from apps), then `graph.update()`. There is no `#isolation` default, so a caller must name an isolation: a synchronous nonisolated caller cannot compile the call, and an async caller that passes another actor hops to it. `TesseraHarness` gains the internal `@MainActor` `Driver`, a shell over that step: it owns the app (built by the registry factory), the `ViewGraph` and its base environment, and a `TerminalSession`; `step(_:)` calls `Step.run(…, isolation: MainActor.shared)` and then `session.draw` when `graph.needsRender`, and the host stops after the step that sets `isFinished`. The step order and update policy are ported from the review loop's `ApplicationDriver`, without its `isolated TerminalSession` hosting and its hard-coded `q`. `HeadlessHost` (a session over `InMemoryTerminalDevice` into one persistent Ghostty virtual terminal) and `LiveHost` (a session over the real device inside `withApplicationTerminal`, handing its scope a main-actor function value rather than the generic driver, as the spec's runtime section explains) share the `Driver` and the `draw` path. The harness has no quit key and no Tab policy. Tessera's own nonisolated demos may additionally be stepped on per-test actors, one actor per test (an internal shell over the same `Step.run` with `isolation: self`), which keeps parallel suites parallel; that shell is not public.

`Examples/Sources/DemoSupport`: `Demo` is an `Application` that declares its registry name, minimum size, `viewports`, and `fixtures` (further registrations of the same demo), no defaults; `DemoSupport` registers every demo into one `ApplicationRegistry`. A demo handles its own quit key in `apply` (whole-key matching through a shared `isQuitKey` helper, never `Key` equality on enriched keys) and reports through `isFinished`. The first demo, a counter built from landed primitives, proves the path; Slice 6's Text demo may absorb it. The `mobile` rule is decided (Decision 1, (b)): `mobile` is 40 columns at natural height, derived through a package-level nil-height proposal on `ViewGraph` plus two-height detection, so a height-greedy demo fails `size mobile` with an error naming `mobileScreen` (40x16). Demos follow the rules in [Developer tooling](../architecture/developer-tooling.md#demos): interactive, every variable style shown, extra controls allowed for complex components, no workarounds for library bugs.

### 7 Library fixes from the first demos

Owner decisions Q14-Q16 (2026-10-25). The Slice 6 demos exposed library defects, recorded in Discoveries: a graph rooted at an `@ViewBuilder` body is dirty after every `update()`, every step of `stacks`, `flex`, and `foreach` reports `layoutEnvironmentChanged`, a `Spacer` with `layoutPriority(1)` takes the whole remainder, `Flex` fill weights invert when its children are larger than the space, and `Flex` takes no alignment. The demos work around or pin them today, so they are fixed here, right after Slice 6 and before Flow and `ViewThatFits` build on the same layout code; the harness still never compensates for a library bug. Five fixes in one reviewable step. (i) A graph rooted at an `@ViewBuilder` body is clean after an `update()` that changes nothing: the builder wraps even one view in a `TupleView`, which is not equatable, so the root is re-evaluated and marked every time, and the slice makes reconciliation skip an unchanged root. (ii) Reconciliation stops reporting `layoutEnvironmentChanged` and `renderEnvironmentChanged` for an unchanged environment: stacks rebuild their children's `EnvironmentValues` on each update and reconciliation compares storage by identity (`===`); the slice chooses between comparing by value and keeping one storage across updates, and records the choice under Decisions. (iii) Q15: a higher `layoutPriority` tier receives the remaining space minus the minimums of all lower-priority children (SwiftUI's rule), not the whole remainder, so `HStack { L; Spacer().layoutPriority(1); M; Spacer(); R }` keeps `M` and `R` on screen. The slice amends step 3 of `docs/spec/phase-4/slice-02-layout-protocol-and-stacks.md` and its priority-tier distribution tests in the same change; the amended wording says how rigid children, the reserved minimums, and the integer remainder rule interact, and the slice notes in Discoveries whether Flex's own tier rule needs the same reservation. (iv) `Flex` fill weights stop inverting when the children are larger than the space: the slice settles the rule against the negative-remainder text of the Flex spec (`docs/spec/phase-4/slice-02-5-flex-and-splitview-negotiation.md` and `docs/design/primitives/flex.md`: `fill` allocations are removed by weight toward zero, equal-tier remainder cells from later children first) and amends whichever of the code and the text is wrong. (v) Q16: `Flex` gains `alignment: FlexAlignment = .start` with cases `.start`, `.center`, and `.end`, the cross-axis placement of a child smaller than the cross extent, relative to the axis, like CSS `align-items`; there is no `stretch` and no main-axis justification for now. The default keeps today's frames (`.start` is the leading edge: `VerticalAlignment.top` for a horizontal `Flex`, `HorizontalAlignment.leading` for a vertical one), and `docs/design/primitives/flex.md` (its cross-axis placement sentence and public initializer) and the Flex spec are updated in the same change. `Flex`'s `min(n)` floor on a non-wrapping `Text` child stays with Text wrapping (Slice 9).

Delivers: a graph is clean after an idle step, an unchanged environment is not reported as changed, a high-priority `Spacer` no longer pushes lower tiers past the edge, oversized `Flex` fill weights keep their order, and `Flex` aligns children on its cross axis. Verify: an idle step of the `stacks`, `flex`, and `foreach` demos reports no environment reasons and draws nothing (`drew: false`, no bytes); the `stacks` demo drops the neighbour priorities it uses as a workaround; the `flex` demo shows `.center` and `.end`, and its scenario pins the frames; distribution-table tests cover the reserved minimums and oversized fill weights; goldens change only where these fixes move frames.

## Unattended execution

Rules for an agent running slices of this plan without the owner.

- Base: this plan's current decisions live on the docs branch `docs/phase-4-decisions` until its pull request merges, and on `main` afterwards. Create each run's worktree from that base with `wt switch --create BRANCH --base origin/docs/phase-4-decisions` (or `--base origin/main` once it has merged), so the worktree hooks run, and do all work there; the `main` worktree is not touched.
- Branches and pull requests: one branch and one draft pull request per slice, with a Conventional Commit title. Slice 1 is `phase-4/01-terminal-colour-reports`; Slice N is `phase-4/NN-<short-name>`. A slice that depends on an unmerged slice branches from that slice's branch and targets it; every other pull request targets the docs branch until it merges and `main` afterwards. Commit at least once per slice and push after each commit so CI runs.
- Never: push to `main`, merge a pull request, force-push a branch another run uses, delete a branch, worktree, tag, or release, create tags or releases, or change repository settings or rulesets.
- Checks before each commit: the `AGENTS.md` gate, `mise run quality:format`, the full `swift test` on the baseline toolchain (`DEVELOPER_DIR=/Applications/Xcode-26.6.0.app/Contents/Developer`), and `mise run quality:lint`; add `mise run docs:lint` when DocC or public API changes, and `swift test --package-path Examples` once the Examples package carries the change. mise is not activated in a plain shell; use `mise exec --` or `mise run`. A new worktree needs `npm ci` before `quality:format`.
- VMs: the Lima guest `tessera-linux` and the UTM guest `tessera-windows-11` are shared between runs; start them with `mise run vm:linux-start` and `mise run vm:windows-start`, deliver a worktree with the `*-push` tasks, run one VM test at a time per guest, and leave them running at the end.
- CI waits: watch runs with `gh run watch` or `gh run view`; a hosted-runner flake (a cancelled leg, a runner that never starts) is retried once with `gh run rerun --failed` and recorded in Discoveries.
- Handoff: after each slice, check its box only with evidence on the line (a SHA, a run ID, a command and its result), update `Next:`, and record Decisions and Discoveries as they happen. The run will outlast one context; the plan is the handoff. Plan edits made on a slice branch land with that slice's pull request.
- Owner decisions: a slice whose text names an open decision does not start until the decision is recorded under Decisions. A design question a slice meets that its catalog doc, the spec, and this plan do not answer is recorded in the slice and in Discoveries with a proposed answer, and the slice continues only where the answer cannot change public API or a catalog doc's promises.
- Stuck: before recording a slice as blocked, spawn an `architect` agent at medium effort with the slice, what was tried, and the first error, and try what it proposes. Record its advice and the result in Discoveries either way.
- Blocked slices: record what was tried, the architect's advice, and the first error in the slice, leave the box unchecked, and stop that run's chain; slices that do not depend on it may still run.
- Left for the owner: reviewing and merging the pull requests, and every open decision.

A scratch SwiftPM package with real separate modules (a path dependency on this checkout) settled the rule: it is the compiler mode of the module that writes the extension, not which module declares the type. Plain Swift 6 mode is an error ("crosses into main actor-isolated code and can cause data races") for a type declared `@MainActor` and for one isolated through its module's default isolation, in the same module or another, on Swift 6.3.3 and 6.4. With `.defaultIsolation(MainActor.self)` in the extension's module it builds on both. With `InferIsolatedConformances` it builds on both for a type declared `@MainActor`; for a type isolated only through its own module's default isolation it builds on 6.4 but errors on 6.3.3 when the extension is in another module. The first version of this note and of the docs said the difference was same module versus another module; that generalised from one cross-module `swiftc` run on 6.3.3 whose type was isolated only through default isolation, which is the 6.3 corner above, and the two-module package disproved it.
