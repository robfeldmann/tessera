# Build the Phase 4 view layer with the tooling that proves it

Goal: Tessera's 1.0 view layer (styling, focus, pointer, scrolling, controls, collections, SplitView, the remaining views, and an intro app) lands component by component from the `ready` catalog docs, and every component arrives with a demo that runs live and headlessly, a scenario that an agent can run without prose, and the harness checks that catch the defect classes the archived attempts missed. When this is done, `mise run dev:run Examples/Scenarios` passes on macOS and Linux, `conform` gates every `implemented` catalog page, and a fresh agent given only the `tessera-devtools` skill can drive a demo, read a failure, and take a shot.

This plan merges plan 032 (Phases 8-17, its open implementation phases; Phases 1-7 are complete and stay there as history) and plan 033 (the developer tooling, with its spikes, decisions, and owner feedback). Both are cancelled and link here (plan 035 Step 6.3).

## Approach

Current state. `main` carries Phase 4 Slices 1, 2, and 2.5 (`TesseraCore`, `TesseraLayout`, the first `TesseraWidgets`: `ViewGraph` reconciliation, stacks, Flex, static `SplitView` and `ScrollView`), the omp2-reviewed design catalog in `docs/design/` (every component doc is `ready` or close to it), the amended spec (`docs/spec/phase-4/`), and the five tooling spikes under `spikes/` with the seams spike saved as `spikes/Seams/30e4bbf.patch`. Plan 034 fixed the two defects the spikes found in the runtime: nested view lists now lay out element by element (so demos can use `ForEach`), and the Examples package builds in CI. libghostty-vt comes from a prebuilt artifact bundle ([libghostty-vt distribution](../architecture/libghostty-vt-distribution.md)), so no build or test job runs Zig. The toolchain lanes are Swift 6.3.3 (baseline) and 6.4 (`docs/architecture/toolchain-lanes.md`); tasks are mise tasks (`mise run …`), and the docs are the `docs/` IWE workspace.

End state. The components of `docs/spec/phase-4/` "The 1.0 surface" are implemented and graduated into DocC, each demo is a snapshot fixture at its declared viewports, `Examples/Scenarios/` is the behaviour corpus that CI runs on macOS, Linux, and Windows, and `TesseraRuntime` (the `Application` contract, re-exported by `Tessera`), `TesseraHarness` (root package; the library app authors import to drive and check their own apps), `Examples/Sources/DemoSupport`, and `Examples/Sources/TesseraDev` (the target of the `tessera` executable) are the tooling that plan 033 designed.

Patterns to follow. Each step starts from a `ready` catalog doc (finishing it is the first part of the step). Each component lands with its tests, its demo, and its scenario in one reviewable step; port from the archive tags (`archive/phase4`, `archive/phase4-review-loop`, `archive/phase4-unicode-demo-stash`, `archive/catalog-workbench`) only after reading the code against the doc, using the port map in `docs/research/phase-4-salvage-review.md`. Measurement and `body` stay pure; every `NodeState` row has one owner; collections key by stable IDs and fail closed on duplicates. The harness never compensates for a library bug (demos find bugs; the library is fixed). Text goldens are the only committed artefacts; drift fails without `--record`. No test affordances in product API: `TesseraCore` gains only value-typed diagnostics fields, each by spec amendment. A slice that adds or changes a tool updates [Developer tooling](../architecture/developer-tooling.md) (or the per-tool page it links) and the `tessera-devtools` skill before the slice is checked off, so the page describes the tools as built plus what is still only designed, and agents building later slices use the skill as they go. The app contract is Decision 9 (i) and the spec's [Runtime isolation](../spec/phase-5-runtime-and-polish.md#runtime-isolation) section: `Application` carries no isolation, a host is a `@MainActor` shell over one nonisolated step that takes `isolated any Actor`, and isolation mistakes are proved by compile-fail fixtures, never by `assumeIsolated`. The harness's public names are the seven the stable-surface decision lists; every other declaration in it is `package` or internal. "Demo" is the word for Tessera's own per-component example apps; the CLI and the scenario header say `app`.

Patterns to avoid. The Showcase (a monolithic demo app) and the archived batch attempts; porting review bundles or committed captures; a `wait` that sleeps; prints as the way to answer "why".

Files that orient a newcomer. [Developer tooling](../architecture/developer-tooling.md) (what the tools are and how they fit), `docs/spec/phase-4/architecture.md`, `docs/spec/phase-4/testing-posture.md`, `docs/design.md` (status ladder, wireframes, table schemas, graduation), `docs/design/tokens.md` (viewports, roles), `docs/design/translation-key.md`, `docs/research/phase-4-salvage-review.md`, the five spike READMEs under `spikes/`, and plan 033's "Tool surface" section (kept verbatim in the cancelled plan, which this plan cites rather than repeats).

Non-goals. A `TesseraTern` backend (Tern Surface Protocol output), modal overlays, and post-1.0 views stay out.

Open questions: Decision 9 (iii) below (how an app gets `tessera`); (i) and (ii) are decided.

The slice also makes `TerminalSession.draw` caller-isolated, as the spec's [Runtime isolation](../spec/phase-5-runtime-and-polish.md#the-session) section specifies (2026-10-23 runtime isolation decision): `nonisolated(nonsending) public func draw<R>(_ body: (borrowing Frame) throws -> R) async throws -> R`. The transaction is acquire the draw gate, begin the frame on the session (`checkOpen`, read the size, fix the rendering policy), run `body` synchronously in the caller's isolation, commit on the session (`checkOpen` again, since the scope can have closed while the body ran; diff against the last drawn buffer, write, flush, record `lastDrawn`), release the gate; only the `Buffer` and cursor cross, as values. The signature loses `sending` on the body and the result, a relaxation, so every existing caller compiles unchanged. That is the only public line this slice changes; nothing new is `public`.

### 3 Harness target, `TesseraRuntime`, and Showcase retirement

Plan 033 Step A.3, plan 032 Step 8.1, and Decision 9 (i). Two new root-package library targets, each with boundary allowlist rows in `scripts/check-package-boundaries.py` and the shared `swiftSettings`; both are listed in [module and file layout](../spec/module-and-file-layout.md).

`TesseraRuntime` holds the app contract now and the Phase 5 runtime later. It depends on `TesseraCore` (for `View`) and `TesseraTerminalInput` (for `InputEvent`), and `Sources/Tessera/Tessera.swift` gains `@_exported import TesseraRuntime`, so `import Tessera` alone declares an `Application`. This slice writes one declaration, in `Sources/TesseraRuntime/Application.swift`, with DocC comments that carry the four adoption shapes of the spec's [Runtime isolation](../spec/phase-5-runtime-and-polish.md#adopting-it) section:

```swift
public protocol Application: AnyObject {
  associatedtype Body: View
  @ViewBuilder var body: Body { get }   // the root view; reads the model, hands out Bindings
  func apply(_ event: InputEvent)       // each event the graph left .ignored; resizes always
  var isFinished: Bool { get }          // default false; the host stops after the step that sets it
}
```

`isFinished` has a default (`false`) in a protocol extension. The protocol refines nothing but `AnyObject`: not `@MainActor` and not `SendableMetatype`, since either would forbid shapes the spec supports. `Tests/TesseraRuntimeTests` (a new test target) imports only `Tessera` and compiles the adoption shapes that need no special module: a plain class, an `@Observable` class, a `@MainActor final class` declared `: @MainActor Application`, and `extension Counter: Application {}` for a nonisolated type; the default-main-actor shape is pinned by Slice 4's fixtures.

Move the spike code with its goldens byte-identical before any addition, platform code into per-OS `sources:` shims. App authors will import it from test and dev targets (2026-10-22 decision), so its public names are chosen for them from the start: only the stable-surface names (2026-10-23 decision) are ever `public`, none of them in this slice, and it uses the root package's `package` seams internally without re-exporting them. Any spike type that stands in for the app contract stays `package` here and is replaced by `Application` in Slice 4. Delete `Examples/Sources/TesseraShowcase/`, its tests, the `core:showcase` task, and its mentions in `README.md`, `docs/project-status.md`, `CONTRIBUTING.md`, and the changelog's unreleased notes.

### 4 Registry, viewports, the main-actor driver, and `tessera launch`

Plan 032 Step 8.2 and plan 033 Step B.1, under Decision 9 (i) and the spec's [Runtime isolation](../spec/phase-5-runtime-and-polish.md#runtime-isolation) section. The contract itself landed in Slice 3, and `TerminalSession.draw` has been caller-isolated since Slice 2.

`TesseraHarness` gains two public names. `ApplicationRegistry` has `init()` and `mutating func register<App: Application>(_ name: String, minimum: TerminalSize? = nil, viewports: [Viewport], make: @escaping @MainActor () -> App)`. It is the one selection point; the harness opens factories on the main actor, once per run, so each run starts fresh and a fixture is one more registration (`register("browser-empty") { Browser(fs: .empty) }`). A duplicate name makes every entry point that reads the registry fail (exit 3, or a failing report), never last-wins; registration itself does not throw (the spike's did; do not copy it). A `@Sendable` factory for a main-actor app is a compile error at the registration site. `Viewport` is a `Hashable, Sendable` enum: `desktop` (80x24), `mobile`, `mobileScreen` (40x16), `custom(TerminalSize)`.

Everything else is `package`. `TesseraRuntime` gains the canonical step, a nonisolated `package` function that takes the host's isolation as a parameter, written as the spec's [canonical step](../spec/phase-5-runtime-and-polish.md#the-canonical-step) has it (`Step.run(_ app:graph:event:isolation: isolated any Actor)`, returning the `EventDisposition`): resize the graph if the event is a `.resize`, `graph.dispatch`, `app.apply(event)` when the disposition is `.ignored` or the event is a resize (a resize is never routed, so Slice 9's routing cannot take it from apps), then `graph.update()`. There is no `#isolation` default, so a nonisolated caller cannot compile the call. `TesseraHarness` gains the `package` `@MainActor` `Driver`, a shell over that step: it owns the app (built by the registry factory), the `ViewGraph` and its base environment, and a `TerminalSession`; `step(_:)` calls `Step.run(…, isolation: MainActor.shared)` and then `session.draw` when `graph.needsRender`, and the host stops after the step that sets `isFinished`. The step order and update policy are ported from the review loop's `ApplicationDriver`, without its `isolated TerminalSession` hosting and its hard-coded `q`. `HeadlessHost` (a session over `InMemoryTerminalDevice` into one persistent Ghostty virtual terminal) and `LiveHost` (a session over the real device inside `withApplicationTerminal`, handing its scope a main-actor function value rather than the generic driver, as the spec's runtime section explains) share the `Driver` and the `draw` path. The harness has no quit key and no Tab policy. Tessera's own nonisolated demos may additionally be stepped on per-test actors, one actor per test (a `package` shell over the same `Step.run` with `isolation: self`), which keeps parallel suites parallel; that shell is not public.

`Examples/Sources/DemoSupport`: `Demo` is an `Application` that declares its registry name, minimum size, `viewports`, and `fixtures` (further registrations of the same demo), no defaults; `DemoSupport` registers every demo into one `ApplicationRegistry`. A demo handles its own quit key in `apply` (whole-key matching through a shared `isQuitKey` helper, never `Key` equality on enriched keys) and reports through `isFinished`. The first demo, a counter built from landed primitives, proves the path; Slice 6's Text demo may absorb it. The `mobile` rule is decided (Decision 1, (b)): `mobile` is 40 columns at natural height, derived through a package-level nil-height proposal on `ViewGraph` plus two-height detection, so a height-greedy demo fails `size mobile` with an error naming `mobileScreen` (40x16). Demos follow the rules in [Developer tooling](../architecture/developer-tooling.md#demos): interactive, every variable style shown, extra controls allowed for complex components, no workarounds for library bugs.

`Examples/Sources/TesseraDev`, the target of the `tessera` executable product in the Examples package, is created here as `HarnessCLI.main(registry:)` (public, `async -> Never`) with `apps` (list the registry) and `launch NAME` (run one app live in this terminal) and `help COMMAND`; Slice 5 adds the rest. `mise-tasks/dev/apps` and `mise-tasks/dev/launch` mirror them (each with `#USAGE`). Check that the `tessera` executable and the `Tessera` library do not collide on case-insensitive file systems (macOS, Windows).

Isolation is pinned by two compile-fail fixtures beside `Tests/CompileFailFixtures/FrameRegionEscape.swift`, run by a script beside `scripts/check-frame-region-ownership.sh` and called from `mise-tasks/quality/architecture` the same way (`swiftc -typecheck` against the debug modules, an expected-diagnostic substring, and a positive control for each, so a toolchain that stops diagnosing fails the check instead of passing). First, an actor host given a main-actor app: `Browser: @MainActor Application` stepped from an actor through `Step.run(…, isolation: self)`; expect "main actor-isolated conformance of 'Browser' to 'Application' cannot be used in nonisolated context" (Swift 6.4 adds "cannot be used in actor-isolated context", so match the shared prefix); the control is the same app on a `@MainActor` host. Second, a default-main-actor type adopted from another module without `@MainActor` on the conformance: a module compiled with `-default-isolation MainActor` declares `Journal`, and a second module writes `extension Journal: Application {}`; expect "crosses into main actor-isolated code and can cause data races"; the control is `extension Journal: @MainActor Application {}`. No exit tests are needed, because no path carries an `assumeIsolated`.

Create `.agents/skills/tessera-devtools/SKILL.md` with what this slice makes usable (`tessera apps`, `tessera launch NAME`, a demo's headless snapshot test) and an `AGENTS.md` pointer to it; later slices extend it.

Delivers: one demo steps through one driver, headless and live: `tessera launch NAME` runs it in a terminal and a snapshot test renders it identically through the in-memory device. Verify: registry tests cover lookup and duplicates (every reading entry point fails); a greedy demo fails `size mobile`; one demo's snapshot test is a few lines, and it is the test that renders a `ViewGraph` through `TerminalSession.draw` into an `InMemoryTerminalDevice` and asserts the bytes the device received, which restores the coverage the retired Showcase's `ShowcaseTerminalSessionTests` gave; a nonisolated demo steps on a per-test actor and on the main actor through the same `Step.run`; both compile-fail fixtures fail with their expected diagnostics (Slice 3 checked the second one: a type from a default-main-actor module, extended in another module without `@MainActor`, is diagnosed with and without `InferIsolatedConformances` in the extension's module, so the fixture needs no flag handling), their controls compile, and `mise run quality:architecture` runs them; the `.resize` rule is in the step's doc comment and Slice 9's routing tests pin it once `dispatch` can consume events. `DemoSupport` re-adds the `Tessera` product to the Examples manifest and so replaces `Examples/Sources/ApplicationConsumer`, the one-file guard Slice 3 added for `import Tessera` from outside the root package; delete it here.

### 5 Scenario language, runner, the `tessera` CLI, and the CI corpus

Plan 033 Steps B.2 and B.3. `Examples/Scenarios/README.md` is the grammar (one statement per line, shell quoting, `#` comments; `app`, `size`, `term` header; `resize`, `key`, `type`, `paste`, `bytes`; `shot`, `tree`, `dump`; `expect text|screen|cell|node|cost`; `check`; the "not yet expressible" table for `wait`, `settle`, `focus`, `mouse`). Header-binding, fail-fast parser (`FILE:LINE: error:`; an unknown statement is a parse error, so a scenario that uses a newer statement fails loudly on an older harness); the runner continues after a failed expectation; one `ScenarioReport` yields the human and JSON forms; `--record`, `--repeat N`, `--timing`; exit 0 pass, 1 expectation failed, 2 usage or parse error, 3 harness error; one JSON object per command on stdout when stdout is not a terminal. `HarnessCLI.main(registry:)` (created in Slice 4 with `apps` and `launch`) gains `run PATH...`, `shot`, `tree`, `check`, and `replay`; `mise-tasks/dev/*` mirror every command (`dev:apps`, `dev:launch`, `dev:run`, `dev:shot`, …, each with `#USAGE`); `help COMMAND` prints real text. The other three public names land here: `ScenarioRunner` (`init(registry:record:)`; `run(_ paths: String...) async -> [ScenarioReport]`, which takes what `run PATH...` takes and returns one report per scenario, so the Swift entry point and the CLI are not an asymmetric pair), `ScenarioReport` (`scenario`, `passed`, `failures`, `description` for the human form, `json: String`), and `ScenarioFailure` (`line`, `statement`, `verb`, `message`); nothing else in the harness is `public`. The README ends with the stability rules of [Developer tooling](../architecture/developer-tooling.md#stability), so the grammar's single source says what is promised at 1.0. CI: the `test` matrix's macOS, Linux, and Windows legs run `swift test --package-path Examples` and `tessera run Examples/Scenarios`, all required (Decision 7); a `.gitattributes` rule checks goldens out with LF on every platform, so Windows' CRLF checkout cannot drift them. Amend the spec's [testing posture](../spec/phase-4/testing-posture.md) so scenarios, the harness, and `check` sit beside snapshots and unit tests as a testing layer, pointing at [Developer tooling](../architecture/developer-tooling.md) for the design; later tooling slices keep that page current the same way. The harness answers the terminal's colour queries itself, from the scenario's `term` header (colours known with given values, or unknown), so a styled golden never depends on the Ghostty virtual terminal's default colours.

Verify: two runs give identical bytes; a parse error under `--json` is a failure with verb `parse`; a drifted golden fails without `--record`; the CI probe (break a scenario, watch the run fail, revert); the Windows leg passes the corpus with goldens checked out by Git for Windows' defaults.

## Unattended execution

Rules for an agent running slices of this plan without the owner.

- Base: this plan's current decisions live on the docs branch `docs/phase-4-decisions` until its pull request merges, and on `main` afterwards. Create each run's worktree from that base with `wt switch --create BRANCH --base origin/docs/phase-4-decisions` (or `--base origin/main` once it has merged), so the worktree hooks run, and do all work there; the `main` worktree is not touched.
- Branches and pull requests: one branch and one draft pull request per slice, with a Conventional Commit title. Slice 1 is `phase-4/01-terminal-colour-reports`; Slice N is `phase-4/NN-<short-name>`. A slice that depends on an unmerged slice branches from that slice's branch and targets it; every other pull request targets the docs branch until it merges and `main` afterwards. Commit at least once per slice and push after each commit so CI runs.
- Never: push to `main`, merge a pull request, force-push a branch another run uses, delete a branch, worktree, tag, or release, create tags or releases, or change repository settings or rulesets.
- Checks before each commit: the `AGENTS.md` gate, `mise run quality:format`, the full `swift test` on the baseline toolchain (`DEVELOPER_DIR=/Applications/Xcode-26.6.0.app/Contents/Developer`), and `mise run quality:lint`; add `mise run docs:lint` when DocC or public API changes, and `swift test --package-path Examples` once the Examples package carries the change. mise is not activated in a plain shell; use `mise exec --` or `mise run`. A new worktree needs `npm ci` before `quality:format`.
- VMs: the Lima guest `tessera-linux` and the UTM guest `tessera-windows-11` are shared between runs; start them with `mise run vm:linux-start` and `mise run vm:windows-start`, deliver a worktree with the `*-push` tasks, run one VM test at a time per guest, and leave them running at the end.
- CI waits: watch runs with `gh run watch` or `gh run view`; a hosted-runner flake (a cancelled leg, a runner that never starts) is retried once with `gh run rerun --failed` and recorded in Discoveries.
- Handoff: after each slice, check its box only with evidence on the line (a SHA, a run ID, a command and its result), update `Next:`, and record Decisions and Discoveries as they happen. The run will outlast one context; the plan is the handoff. Plan edits made on a slice branch land with that slice's pull request.
- Owner decisions: a slice whose text names an open decision does not start until the decision is recorded under Decisions. A design question a slice meets that its catalog doc, the spec, and this plan do not answer is recorded in the slice and in Discoveries with a proposed answer, and the slice continues only where the answer cannot change public API or a catalog doc's promises.
- Stuck: before recording a slice as blocked, spawn an `architect` agent at medium effort with the slice, what was tried, and the first error, and try what it proposes. Record its advice and the result in Discoveries either way.
- Blocked slices: record what was tried, the architect's advice, and the first error in the slice, leave the box unchecked, and stop that run's chain; slices that do not depend on it may still run.
- Left for the owner: reviewing and merging the pull requests, and every open decision.

## Discoveries

- `ForEach` and other view lists inside stacks laid every item at the same frame (spikes 1, 2, and 4; plan 033) — fixed by plan 034 Step 10.1 (`f4172e8`), with `siblings-disjoint` as the harness rule that would have caught it.
- A `SplitView` pane whose content is a nested multi-view list now places only its first view (plan 034 Step 10.1 discovery) — Slice 15 settles the rule.
- `Text` does not wrap at HEAD and ignores its width proposal (plan 033) — Slice 8.
- `handlerKinds` and the focus and requirement counters are dead at HEAD (plan 033; `focusChanges` confirmed in plan 034 R-10) — Slice 9.
- The seams spike's `sizeChanges` fan-out was superseded by plan 034 Step 6.6, which fans one subscription out newest-only — Slice 2 adapts the patch rather than applying it.
- A `@MainActor` host could not present through `TerminalSession.draw`: its closure and result were `sending`, so a main-actor caller could not send its graph in (decision 9 (i) record, result 4). The runtime isolation decision relaxes `draw` to `nonisolated(nonsending)` — Slice 2. The Phase 5 sketch of `TestRuntime(scene:)` did not compile either (`borrowing var body`, an undefined `EventRouting`) and is gone from the spec.
- A device whose input has finished (the default `InMemoryTerminalDevice`) never waits on a probe timeout: `finishInput()` marks the coordinator closed and every round resolves at once, so an injected `probeSleep` is observable only on an open device. The seams README's "waits out `activeProbeTimeout`" holds for an input stream that never finishes. Slice 2's probe-sleep test uses `keepsInputOpen` for this reason.
- `--filter TerminalSessionTests`, the Slice 2 Verify command, matches the test's source file name, since the session tests are free-function `@Test`s; the seam tests live in `TerminalSessionTests.swift` so the filter runs them.
- `TerminalSession.outputTap` is actor-isolated state, so the harness sets it inside `withApplicationTerminal`'s `isolated` body or through an `isolated TerminalSession` parameter, never from outside the actor — Slice 3's driver takes the session that way.
- swift-format rewrites a final closure argument into a trailing closure, then flags the call for also carrying a labelled closure (`OnlyOneTrailingClosureArgument`; SwiftLint `multiple_closures_with_trailing_closure`), so tests bind injected clocks and sleeps to locals before passing them. swift-format also indents a modifier-only `nonisolated(nonsending)` line above a declaration, so the attribute sits inline with the other modifiers.
- A draw's body now runs in the caller's isolation, so the scope that owns the session can close between `beginFrame` and the commit; before, only the `io.size()` suspension left that window. `commitFrame` therefore checks that the session is open before it encodes, taps, or writes, and a draw caught in the window throws `TerminalSessionError.closed` with the renderer and `lastDrawn` untouched (critic review of PR #59, F1). The regression holds the draw at its size read, which opens the same window deterministically without a blocking body. `InMemoryTerminalDevice.resize(to:)` stays the silent public form and `deliverResize(to:)` the package form that also emits; the doc on `deliverResize` says so (F2).
- The spike's 18 tests pass at their new home on today's runtime without a changed expectation, so the corpus's identity strings (`root/index(2)/id(catalog)` and its siblings) and the natural-height probe are still valid after plan 034.
- `Tessera` does not re-export `Observation`, so the `@Observable` adoption-shape test imports it beside `Tessera`: the plan's "imports only `Tessera`" holds for every Tessera module, and an app author's `@Observable` model needs `import Observation` whatever else it adopts.
- A `"\r\n"` is one `Character`, so `"a\r\nb".split(separator: "\n")` yields one piece. Slice 5's parser should split on `\n` and tolerate `\r`, or normalise line endings, rather than rely on `.gitattributes` alone, because an app author's scenario files may be checked out with CRLF.
- SwiftLint in new files: a `disable:next` comment between a doc comment and its declaration orphans the doc comment (`orphaned_doc_comment`), so the disable goes on the declaration's own line (`disable:this`); a bare `disable` needs a later `enable` (`blanket_disable_command`).
- The critic review of PR #64 (F1) found the `Application` docs and the spec promised a compile error for `extension Notes: Application {}` on a main-actor type that does not appear in every mode. Scratch typechecks on Xcode 26.6 settle it: inside the module that declares the type, plain Swift 6 mode diagnoses it ("crosses into main actor-isolated code and can cause data races"), while `-default-isolation MainActor` and the `InferIsolatedConformances` upcoming feature (which this package's shared `swiftSettings` and the Examples manifest enable) infer the isolated conformance and compile it; from another module, which is the test-or-dev-target case the sentence was written for, it is diagnosed in both modes, and `extension Journal: @MainActor Application {}` compiles. The docs and the spec now say exactly that.
- The critic review of PR #64 (F2) noted that after the Showcase left, no test renders a `ViewGraph` through `TerminalSession`, and nothing compiled `import Tessera` from outside the root package. The first stays open until Slice 4's driver snapshot test (its Verify line now says so); the second is guarded by `Examples/Sources/ApplicationConsumer`, a one-file library target that declares a nonisolated and a main-actor `Application` against `import Tessera` only, so the Examples build in CI fails if the re-export goes.
- The critic review of PR #64 (F3) found `CLI.swift` had no caller and no test, so it was removed from the harness. `ScenarioReport.human()`, `ScenarioReport.parseFailure(_:)`, `ShotArtifact`, and the artifacts `ScenarioRunner.execute` returns now have no caller either; they are the report's human form, the parse-failure report, and the `--out` payload that Slice 5's runner and CLI build on, and they stay as moved so the port stays byte-for-byte before any addition.
